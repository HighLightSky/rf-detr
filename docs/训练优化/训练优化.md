# 训练加速方法与尝试总结

> 记录 2026-08 期间围绕 SHWX 遥感小样本检测实验（Ret-SSCL 分支）所做的训练加速方法与尝试。
> 硬件基线：RTX 5090 32GB + 20 核 CPU + bf16。本文覆盖「本次未提交的改动」与「此前已提交的相关工作」两部分。

## 1. 瓶颈分析

SHWX 遥感数据 + AUG_AERIAL 增广 + Mosaic 的训练管线，实测瓶颈按优先级排列：

1. **CPU 侧数据管线**：JPEG 解码（大尺寸遥感图）、Mosaic 拼接、Albumentations 增广全部在 CPU 串行执行，worker 数再多也受线程池争抢限制；
2. **dynamo 运行时开销**：torch.compile 开启 dynamic=True 时，guard 检查与符号形状追踪在 CPU 上持续占核，小 batch 下 GPU 空闲、step 时间被固定开销主导；
3. **匈牙利匹配串行**：per-image 的 SciPy `linear_sum_assignment` 在 batch 内串行求解，目标数多时成为每步 CPU 延迟点；
4. **验证阶段开销**：验证前向、loss 计算、EMA/非 EMA 双模型前向占用训练时间与显存。

## 3. torch.compile 全面适配（暂存区）

### 3.1 门控重写：按「实际生效 scale 数」决定 dynamic

原逻辑：`compile` 仅当 `multi_scale=False` 时生效，且无条件 `dynamic=True`。

新逻辑（`module_model.py::_effective_input_scales` + 门控）：

- 推导训练时**实际**出现的输入边长集合：
  - `multi_scale=False` → 固定 `[resolution]`；
  - `multi_scale=True` → `compute_multi_scale_scales()` 展开候选集；
  - `do_random_resize_via_padding=False`（默认）→ `skip_random_resize` 只保留最大单一 scale；
- 单一 scale → `dynamic=False`：输入形状静态，guard 检查最省 CPU。实测 dynamic=True 的 dynamo 运行时开销持续吃 **5+ 核 CPU**（小 batch 下 GPU 闲置、step 时间被固定开销主导）；
- 多 scale → `dynamic=True`：一个编译图覆盖所有 (H, W) 变体，避免逐 shape 重编译风暴。

`capture_scalar_outputs=True` 保持开启：`gen_encoder_output_proposals` / `ms_deform_attn` 把空间形状 `.item()` 当 Python 切片下标，配合 dynamic 时 item() 结果是 backed symbol，不会触发 `PendingUnbackedSymbolNotFound`。`suppress_errors=True` 保证子图编译失败时回退 eager 而不崩溃。

### 3.2 前置修复清单

| 问题 | 修复 | 位置 |
| --- | --- | --- |
| `torch._shape_as_tensor` 不可被 dynamo 追踪 | 改为 `torch.as_tensor(list(src.shape[2:]))` | `models/transformer.py:332` |
| 编译器过旧：torch>=2.11 的 inductor C++ wrapper 需要 `-std=c++20`，系统默认 g++-9 会**静默失败**（suppress_errors 吞掉错误，训练背着 dynamo 开销跑 eager） | `os.environ.setdefault("CXX", "/usr/bin/g++-13")`（须在 torch.compile 前设置） | 训练脚本头部 |
| PTL/EMA checkpoint 键名带 `_orig_mod.` 前缀导致加载 KeyError 或权重全丢 | 统一剥离前缀：`weights.py::load_pretrain_weights`（`state_dict` 格式与顶层 `model` 键格式两种都处理）、`detr.py::load_weights`、`ema.py` 导出时取 `_orig_mod` 裸模型 | 见左列 |

### 3.3 实测数据

- **提速 1.40×**：B16@640 从 119 ms/step → 85 ms/step；显存反而更低（Inductor 算子融合）；
- 显存上限：compile 下 B32 峰值 ~22.5 GB（安全），B40 OOM；
- 首次训练有数分钟编译开销（后续可复用缓存）。

## 4. DataLoader 优化（暂存区）

### 4.1 worker 单线程化

`module_data.py::_worker_init_fn` 中新增 `torch.set_num_threads(1)`：

- decode/mosaic/拼接是纯 CPU 单线程工作，不需要多线程；
- 不设置时 worker 继承主进程的 torch 线程池，每 worker 数线程 × 数十 worker 与主进程、其他 worker 争抢物理核，产生线程 thrashing，decode/mosaic 反而变慢；
- 单线程是 PyTorch DataLoader 官方推荐做法。

### 4.2 并行度与预取

- `NUM_WORKERS = 16~20`（对齐 20 核 CPU，worker 单线程）；
- `PREFETCH_FACTOR = 4~6`（默认 2），加深预取缓冲，平滑 decode/mosaic 抖动。

## 5. 原始图片解码缓存（更改区，`dataset_cache_mode="raw"`）

### 5.1 设计

`datasets/raw_cache.py::RawImageCache`：

- **只缓存确定性结果**：解码后的 RGB uint8 数组落盘为 `.npz`；随机增广、Mosaic 布局、resize、归一化、目标转换仍在线执行，训练语义不变；
- **指纹防陈旧**：缓存文件名 = SHA256(绝对路径 + size + mtime) 前 24 位，源图变更自动 miss；
- **原子写入**：`tempfile.NamedTemporaryFile` + `os.replace`，进程崩溃不残留半截文件；损坏缓存自动回退重新解码。

### 5.2 接入点

- `CocoDetection` / `YoloDetection` / `_LazyYoloDetectionDataset` 新增 `enable_raw_cache(cache_dir, rebuild)` 与统一 `load_raw()`；
- `MosaicDataset` 的 `_load_raw_coco` / `_load_raw_yolo` 改走同一缓存路径（Mosaic 读取不再重复解码）；
- `TrainConfig` 新增 `dataset_cache_mode` / `dataset_cache_dir` / `dataset_cache_rebuild`（`_namespace.py` 排除出命名空间字段）；
- 缓存目录命名带指纹：`{dataset_file}-{split}-{resolution}-{sha256[:16]}`，指纹含版本、数据集根路径、类型、split、分辨率、分割/关键点开关及元数据文件（`data.yaml` / `*_annotations.coco.json` / `annotations/*.json`）的 size+mtime，数据集改动自动换新目录；
- 默认落盘 `output_dir/dataset_cache`。

### 5.3 效果与状态

- 理论收益：跳过每 epoch 重复的 JPEG 解码（遥感大图解码最贵），Mosaic 读取同样受益；
- 实际收益**待实测**（本轮提交后跑一次对比）；缓存首轮构建有一次性写入开销（`rebuild=True` 可强制重建）。

## 6. 数据增强 GPU 化（Kornia backend）

- `AUGMENTATION_BACKEND = "kornia"`：AUG_AERIAL 的全部变换（翻转/旋转/亮度对比度）都有 Kornia 等价物，CPU→GPU 消除数据管线最大瓶颈；
- `"auto"` 在 CUDA + Kornia 可用时自动走 GPU；不支持的后处理仍走 CPU（`is_gpu_postprocess` 判定）。

## 7. 匈牙利匹配并行化（更改区）

`models/matcher.py`：

- per-image / per-DETR-group 的 Hungarian 求解用 `ThreadPoolExecutor` 并行（SciPy `linear_sum_assignment` 释放 GIL，可真实并行）；
- **默认小矩阵串行**：`max_targets_per_image < 64` 时不加线程，避免调度开销；
- 环境变量 `RFDETR_MATCHER_WORKERS` 可强制指定线程数（`=1` 等价回退串行）；
- 并行与串行结果完全一致（已有测试保证）；收益**待实测**。

## 8. 训练配置层面的省时/省显存手段

| 手段 | 说明 |
| --- | --- |
| 有效 batch 64 = B32×2 或 B16×4 | 优化器/EMA/日志步数减半、GPU 单步 burst 更长、占用更平稳（2026-08-09 实测） |
| `gradient_checkpointing=False` | 5090 32GB + bf16 显存充足时关闭，省去 ~20-30% 重算开销（checkpointing 以计算换显存）；OOM 再开启 |
| `EVAL_INTERVAL = 10` | 减少验证频率，降低 CPU 阻塞 |
| `eval_ema_only=True` | 验证只前向 EMA 模型，省一半验证时间（USE_EMA=True 时 best 指标本就用 EMA）；注意 QNorm-Obj 实验已改回 False 保证非 EMA 对照 |
| `compute_val_loss=False` | 关闭验证 loss 计算，省显存，mAP 不受影响 |

## 9. 关键澄清：训练实际固定 800×800

默认 `TrainConfig`：`multi_scale=True` + `square_resize_div_64=True` + `do_random_resize_via_padding=False` → `skip_random_resize` 只保留最大单一 scale，**训练实际固定 800×800**（并非脚本旧注释以为的 640 / 多尺度）。因此：

- 800×800 输入下单一 scale → `dynamic=False` 编译是安全的；
- 810 基线同样按默认配置跑在 800×800，各实验对照关系不变；
- 旧注释「compile 要求 multi_scale=False」是错误假设，已修正为按实际生效 scale 数门控。

## 11. 后续建议

1. **补实测数据**：原始解码缓存、匈牙利并行两项目前无量化数据，建议在同一环境（5090 + bf16 + compile）下对比 step 时间与 GPU 利用率后回填本文；
2. **沉淀到 AGENTS.md**：脚本注释多处引用「见 AGENTS.md」，但 AGENTS.md 尚无 5090 实测记录，建议把硬件实测数据（B32 ~22.5GB、1.40×、5+ 核 dynamo 开销）同步进去，避免后续会话重复踩坑；
3. **留意 compile 失效风险**：`suppress_errors=True` 会吞掉编译失败，训练可能背着 dynamo 开销跑 eager 而日志无报错（g++ 过旧即此症状），排查 step 变慢时先查编译是否真的生效。
