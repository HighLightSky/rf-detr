## 0. 核心结论（对齐的四个层面）

"文本原型和视觉原型如何对齐"在实现里不是"把两个向量强行弄成一样"，而是四个层面的对齐：

| 层面 | 机制 | 发生位置 |
| --- | --- | --- |
| ① 类别维对齐 | 类别索引/名称/提示词三者同源（`sscl/prompts/shwx.yaml`），产物加载时校验类别数 | 离线构建 + `validate_proto_artifacts` |
| ② 空间维对齐 | 两个不同维度、不同来源的向量各自投影到**统一的融合空间**（256 维），在融合空间做加权求和 | `SimpleProtoFusion`：`proj_v` / `proj_t` |
| ③ 度量对齐 | 融合输出逐槽位 L2 归一化，后续一切相似度都用余弦（与 k-means 聚类、`cosine/tau_p` 打分同度量） | `F.normalize` + `position_score` |
| ④ 语义对齐 | 辅助损失通过 `proto_logits` 把梯度直接送到融合模块参数，让"融合原型"与 GT 类别语义对齐 | `loss_proto_labels` → `fused_prototypes` |

一句话：**视觉原型和文本原型从不直接比较，也不追求向量相等；它们各自被投影到同一个可学习空间，在那里按可学习权重混合，混合结果被归一化成一个统一度量下的类别锚**。

## 1. 两种原型的天然差异（为什么要对齐）

| | 视觉原型 `P_v` | 文本原型 `P_t` |
| --- | --- | --- |
| 来源 | backbone/P4 特征空间（GT 框区域池化 + 余弦 k-means） | CLIP ViT-L 文本编码器（遥感多提示词平均） |
| 维度 | `[25, 10, 256]`（每类 10 槽位子原型） | `[25, 768]`（每类 1 条） |
| 特点 | 细节丰富（形态/纹理/视角），但少样本类噪声大 | 语义泛化强（不依赖样本），但无视觉细节 |
| 存储形态 | 未归一化（聚类中心），加载后冻结 | 未归一化（各 prompt 归一化后取平均），加载后冻结 |

两个空间没有可比性：维度不同（256 vs 768）、语义粒度不同（像素级外观 vs 语言级语义）、分布不同（检测特征空间 vs CLIP 语义空间）。**强行逐元素比较没有意义，所以对齐走"投影到公共空间"的路**（这也是 AGENTS.md 规定"不要直接比较或拼接不同特征空间的向量"的原因）。

---

## 2. 对齐总览（数据流）

```text
视觉原型 P_v [25, 10, 256]              文本原型 P_t [25, 768]
        │                                    │
        │ proj_v: Linear→LayerNorm           │ proj_t: FSemProjection
        │ （视觉→融合空间 256）                │ （768→512→256，Linear→Tanh→Linear）
        ▼                                    ▼
      h_v [25, 10, 256]                    h_t [25, 256]
        │                                    │ 逐槽位广播（每类所有槽位共享同一文本方向）
        └───────────┬────────────────────────┘
                    ▼
   P_mm = normalize( softplus(w_v)·h_v + softplus(w_t)·h_t.unsqueeze(1) )
                    │
           无效槽位置零（valid_slots）
                    ▼
        多模态原型 [25, 10, 256]（每槽位 L2 归一化）
                    │
      ┌─────────────┼──────────────────┐
      ▼             ▼                  ▼
 position_score   enhance_content   loss_proto_labels（语义对齐监督）
 （token·P_mm/tau_p）（槽位交叉注意力）  （GT 类别 CE → 梯度回传 fusion 参数）
```

## 3. 层面①：类别维对齐（同源加载）

视觉原型和文本原型在**构建阶段**就通过同一个文件对齐类别语义：

- `load_class_prompts("shwx")`（[prompts.py:47-88](../../src/rfdetr/sscl/prompts.py#L47-L88)）从 `sscl/prompts/shwx.yaml` 同时加载 `class_names` 与 `class_prompts`，并校验**两个字段的类别索引必须完全一致**，缺失的类别直接报错；
- 构建脚本里 `features_by_class[class_id]` 的 `class_id`、CLIP 编码的 `class_id`、产物里的 `class_names` 全部来自同一份索引（0-24，与数据集 `data.yaml` 的 `names` 一致）；
- 训练加载时 `validate_proto_artifacts` 再次校验 `visual_prototypes.shape[0] == num_classes == len(class_names)`（[artifacts.py:126-140](../../src/rfdetr/sscl/proto_guidance/artifacts.py#L126-L140)），类别数不一致直接抛错；`meta.dataset` 不一致仅警告。

**这一层的对齐是硬约束**：类别索引错位会让"视觉原型第 3 类"对上"文本提示词第 3 类"但两者语义毫无关系，且无法通过训练修复。

## 4. 层面②：空间维对齐（双投影到融合空间）

这是核心机制（[fusion.py:29-102](../../src/rfdetr/sscl/proto_guidance/fusion.py#L29-L102)）。

**视觉投影 `proj_v`**：`Linear(256→256) → LayerNorm`——把聚类中心从原始特征空间搬到融合空间。选 Linear+LN 是因为视觉原型与打分 token 已经在相近的 backbone 特征空间，浅层适配即可。

**文本投影 `proj_t`**：`FSemProjection`（[fsem.py:35-62](../../src/rfdetr/sscl/fsem.py#L35-L62)）——`Linear(768→512) → Tanh → Linear(512→256)`。文本空间与检测空间差异大，需要两层非线性映射；Tanh 让中间激活有界，稳定投影方向。**输出不归一化**，由融合层统一处理。

**为什么投影而不是拼接/直接平均**：

- 拼接会把两个空间的维度和尺度差异原样带进打分，且 768+256 维需要额外的降维层；
- 直接在原始空间加权平均没有意义（两个空间不可比）；
- 投影让"对齐"成为**可学习**的：`proj_v` 负责回答"视觉特征在融合空间里长什么样"，`proj_t` 负责回答"文本语义在融合空间里对应哪个方向"，二者在训练中共同收敛。

**投影空间的选择**：融合空间维度 = decoder hidden dim（256）。这样融合原型可以直接与 `proj_token` 投影出的 encoder token 做点积（余弦），不需要再降维。

## 5. 融合与权重分配（对齐的"混合"部分）

```python
w_v = F.softplus(self.w_v)          # 可学习标量，初始 0.3
w_t = F.softplus(self.w_t)          # 可学习标量，初始 0.7
h_v = self.projectors.proj_v(visual_prototypes)   # [C, M, d]
h_t = self.projectors.proj_t(text_prototypes)     # [C, d]
fused = w_v * h_v + w_t * h_t.unsqueeze(1)        # 文本逐槽位广播
fused = F.normalize(fused, dim=-1)                # 逐槽位 L2 归一化
fused = fused.where(valid_slots.unsqueeze(-1), torch.zeros_like(fused))
```

几个关键设计：

1. **文本逐槽位广播**：每类 M=10 个视觉子原型，但文本原型只有一条。文本方向被广播到全部槽位——每个槽位 = 公共文本语义方向（类别质心）+ 各自的视觉形态偏差。这保持了"类内多形态"表达，同时让每个槽位都携带语义锚。
2. **softplus 与初始权重**：`w_v`/`w_t` 是未约束的标量参数，经 softplus 保证正性。注意 **softplus 有偏移**：参数 0.3/0.7 的实际有效权重是 `softplus(0.3)≈0.854`、`softplus(0.7)≈1.103`，归一化后约 **44% 视觉 / 56% 文本**（不是字面上的 30/70）。设计意图不变——**初始偏向文本**（少样本类视觉原型噪声大，文本作稳定锚），且两个权重在训练中可学习、可偏离。
3. **归一化时机**：视觉原型存储未归一化、文本原型存储未归一化，投影后也未归一化——**融合输出才做逐槽位 L2 归一化**。这样权重不仅决定混合比例，还隐含了调节两分支尺度（norm 大小）的能力，归一化保证后续余弦度量的可比性。
4. **无效槽位**：融合后置零，不参与打分/注意力——少样本类缺槽位时，融合原型只保留有效形态 + 文本方向。

## 6. 层面④：语义对齐（辅助损失的梯度路径）

对齐不是"投影到一起就完事了"，还需要监督信号保证融合原型确实代表类别语义。关键链路：

```text
position_score：
    proto_logits = normalize(proj_token(mem)) · normalize(P_mm)^T / tau_p   # [bs, N, C]
辅助损失 loss_proto_labels：
    对 Hungarian matched foreground 的 proto_logits 做类别均衡 CE（GT 类别标签）
```

梯度路径：`loss_proto_labels → proto_logits → P_mm（fused_prototypes）→ fusion(proj_v, proj_t, w_v, w_t)`。

**这意味着辅助损失不只训练 `proj_token`，也直接训练融合模块的全部参数**（proj_v、proj_t、w_v、w_t）。它给融合空间施加的约束是：

- 与 GT 类别一致的 token 特征，其投影后应与"该类融合原型"相似度最高；
- 不同类别的融合原型彼此要有区分度。

这就是"语义对齐"的实质：**类别标签把视觉信息和文本信息在融合空间里拧到同一个语义方向**。没有这个监督，proj_v/proj_t 只能靠 top-k 选择这个离散、间接的路径学，很容易 no-op（这也是方案文档 §4.3 专门设计辅助损失的原因）。

注意：辅助损失**不要求** `proj_v(P_v)` 与 `proj_t(P_t)` 两个方向重合——它们可以在融合空间里不相等而互补（一个贡献细节、一个贡献语义质心），只要**融合结果**与 GT 语义对齐即可。

---

## 7. 层面③：度量对齐（余弦 + 温度）

- 聚类阶段（视觉原型构建）：余弦 k-means——聚类空间与打分空间同度量；
- 融合输出：逐槽位 L2 归一化——所有后续相似度都是单位球面上的余弦；
- 打分阶段：`proto_logits = cosine / tau_p`（tau_p=0.2，把 [-1,1] 的余弦放大到 [-5,5] 的 logits 区间，增强判别锐度）；
- 内容增强：槽位交叉注意力 `softmax((tgt·P^T)/√d)`——同一度量下的注意力权重。

三个环节共用同一个"单位球面余弦"度量，保证原型在聚类、融合、打分、注意力四个环节语义一致，不会出现"聚类时很分、打分时不分"的度量错位。

## 8. 对齐质量的度量与诊断

代码提供两类现成工具：

**① 原型空间几何**（[prototype_diagnostics.py:41-65](../../src/rfdetr/sscl/prototype_diagnostics.py#L41-L65)，经 `collect_stats` 上报 `prototype_*` 指标）：

| 指标 | 含义 | 对齐健康的标志 |
| --- | --- | --- |
| `prototype_offdiag_cos_mean/std` | 异类原型余弦的均值/标准差 | 均值低（类间分离）、std 适度 |
| `prototype_offdiag_cos_max` | 最像的两个异类原型 | 不应接近 1（否则存在塌缩对） |
| `prototype_effective_rank` | 原型矩阵的有效秩 | 接近类别数（空间未塌缩） |

**② 跨空间关系对齐**（[prototype_diagnostics.py:68-91](../../src/rfdetr/sscl/prototype_diagnostics.py#L68-L91)）：`prototype_relation_alignment(first, second)` 比较**两个不同维度空间的原型类别关系矩阵**（同类/异类余弦模式）的 Pearson 相关系数。这正是 AGENTS.md 规定的跨空间一致性检验方式——不比较向量，比较关系。如果 `proj_v` 融合后的视觉原型与 `proj_t` 投影后的文本原型的类别关系矩阵高度相关，说明两个模态在融合空间里"看到"了相同的类别结构。

监控装配（[module_model.py:967-1018](../../src/rfdetr/training/module_model.py#L967-L1018)）把这些指标周期性写进 tensorboard，训练中即可判断融合原型是否在正常对齐、有无塌缩。

## 9. 局限与改进方向

1. **少样本类的对齐质量受视觉端拖累**：初始 56% 文本权重缓解但未消除——视觉槽位少/噪声大时，融合原型主要靠文本方向，细节能力弱。方向：少样本类提高 `w_t` 的初始值或按类别自适应权重。
2. **投影冷启动**：`proj_v/proj_t/w_v/w_t` 随机初始化（LayerNorm 近恒等、Linear 默认初始化），训练早期融合空间未成形。阶段 A 冷启动 + λ/γ warmup 就是为它设计的；joint120 联合训练则是让它在特征可塑期一起学。
3. **可复现性**：CLIP 编码（`HF_HUB_OFFLINE=1`，本地缓存路径兜底）是确定性的；但视觉原型 k-means 的初始化抽样没有固定全局种子（见 1视觉原型构建详解 §5 的注意），重建产物时类别级差异会传导到融合与对齐指标。
4. **关系蒸馏（可选扩展）**：方案文档 §1.4 提出过 `L_rel = MSE(R_proto, R_sscl)` 让 ProtoGuidance 融合原型与 SSCL 原型库的类别关系矩阵一致——这是"跨空间对齐"的显式监督形式，当前未启用，等两个原型空间都已判别后再考虑。
5. **门控融合（v1.5 规划）**：`GatedProtoFusion`（跨模态注意力提取细节 + 门控 MLP 融合）比当前加权和更细腻，但 v1 以验证有效性为先。
